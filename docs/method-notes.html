Massing Studio — Method Notes

What this tool computes, how it computes it, and — the part that matters most when you cite it — what it does not model at all. Everything below is read from the source code, not from what a plan-and-extrude tool is generally assumed to do. Where the code makes something unclear, this page says so rather than inferring.

Audience Architecture students and staff Method Plan drawing · straight extrusion · no analysis Runs Entirely in the browser Version 1.0.0 · 17 September 2026

Three things to know before you cite a number

  1. Snapping only ever happens once, when a shape is first drawn. The Select tool's move and scale handles read the pointer position directly and never call the snapping function at all, whatever the Snap checkbox says. Draw a rectangle with Snap on and its corners land on exact multiples of the grid (1 m by default) — but drag that same rectangle, or resize it by a corner handle, and it can end up anywhere: off the grid, at an arbitrary fraction of a metre, with nothing on screen to say so and no way to snap it back afterwards. Snapping to an existing shape's own vertex is stronger still: it is checked before the grid, and fires whether or not Snap is on. A coordinate read off this tool is the grid's answer only for a shape that has never been moved.
  2. There is no area anywhere in the interface. The tool computes a signed polygon area internally — the shoelace formula, positive for one winding direction — but only to work out which way an edge faces and to stop a push/pull drag from folding a shape in on itself. It is never shown on screen, never in a properties panel, never in an export. If you want the area of a footprint you have drawn, you compute it yourself from its coordinates; nothing this tool writes down should be mistaken for one.
  3. Nothing here is analysis. The tool draws a plan, extrudes it by a height, and exports the result. No module computes a structural, thermal, daylight or cost quantity of any kind, and there is no solver — iterative or otherwise — anywhere in the source.
01

What it computes

Eight things, and none of them is more than a few lines of arithmetic. There is no solver anywhere in this application — no stiffness matrix, no finite elements, no iteration of any kind.

The one formula worth naming

The area calculation is the shoelace formula, named as such in the source's own comment:

// Shoelace formula — signed area (positive = counter-clockwise in plan coords). sum = Σ (x_i × y_i+1 − x_i+1 × y_i) area = sum / 2

As trap 2 says, this number is never shown to you. It exists only to tell the push/pull tool which way an edge is facing, and to catch a drag that would collapse a shape's footprint to nothing.

02

The model and its conventions

Units

The project state carries a single units field, set once to 'm' when a new project is created. Nothing in the interface reads or changes it afterwards — there is no unit switcher, and the field is never referenced anywhere else in the source. Every number on screen is a metre, because the code never considers it could be anything else.

Coordinates, and which way is up

A shape's points are plan coordinates, x and y, on the page you draw on. Extruding maps plan x to world X, and the extrusion direction — the layer's height, or a push/pull drag — to world Y, which is "up" in the 3D view. Plan y becomes world Z, negated. A point drawn at plan (x, y) sits at 3D (x, 0, −y) before extrusion, then rises to (x, height, −y) at its top, with the whole shape offset upward by its layer's elevation.

Layers as floors

A layer carries an elevation — the height its floor sits at — and a default height, the extrusion every new shape drawn on it receives. Adding a layer stacks its elevation automatically on top of the tallest one that already exists, and nothing checks for an overlap if elevation is set directly instead. In the current interface, though, this is a property of the data model rather than something you can reach: no button, menu or shortcut in the interface ever adds a second layer, and none edits an existing one's elevation, height or colour. Every project therefore has exactly one layer — Ground Floor, at elevation zero, three metres of default height — and the overlap question does not arise in practice.

Shape types

A rectangle, a polygon and a reference line all store an ordered list of points. A circle stores a centre and a radius instead. Every shape, whichever kind, also carries an id, the layer it belongs to, whether it is closed, a height, and a colour — that is the complete set of fields a shape can hold.

Visibility and locking

The two flags do different amounts of work, and neither does what you might assume. Visibility gates three things at once: whether a shape is drawn in the 2D plan, whether it can be clicked there, and whether it gets a mesh built for the 3D view at all — which is also why a hidden shape never reaches an OBJ, STL or PNG export: there is no mesh for those to draw from. Locking is narrower and reaches nowhere near as far: it is checked in exactly one place in the whole source, the same 2D click test that visibility gates — a locked shape still draws, still meshes in 3D, and still exports everywhere. DXF export is the one exception to all of this: it reads the shape list directly rather than the built meshes, and never checks visibility at all, so a hidden shape's geometry still writes to a DXF file even though it never appears in an OBJ, an STL, or a PNG.

Undo and redo

Every edit that calls a snapshot serialises the whole project state to a string and pushes it onto an undo stack, capped at 100 entries; undoing pops it back and parses it. A large imported asset — an image's pixel data, an imported model's raw .obj text — is deliberately kept out of that state, in a separate lookup the source comments explains exists because the snapshot serialises everything on every edit, and an embedded image or model would otherwise be duplicated into every single undo step. The consequence: undo and redo never touch that lookup at all, they only swap the project state back and forth, and removing an image or a model never deletes its data from the lookup either — it simply stops being referenced. So undoing an import removes it from view and redoing it finds the same data still waiting, consistently, in both directions. Nothing is ever stranded or restored inconsistently; the only way that data is ever cleared is starting a new project outright.

03

Import and export — what survives

This is the section with no counterpart in a tool that has methods to document instead of formats to move between. For each one: what a round trip keeps, and what it quietly drops.

DXF export

Every closed shape writes as a single LWPOLYLINE entity — not exploded into individual lines — and every circle writes as a CIRCLE. That choice is deliberate: a polyline re-imports as one connected shape rather than a scatter of disconnected segments, and it is what a real CAD package expects to read.

DXF import

Reads exactly four entity types: LINE, CIRCLE, LWPOLYLINE, and the legacy POLYLINE/VERTEX/SEQEND triple. Anything else in the file — a block, a hatch, text, a dimension — is silently skipped with no count kept anywhere. The only signal the interface gives you is a warning if the file contained none of the four at all; a file with nine supported entities and ninety unsupported ones reports success, with no way to tell from the interface that anything was left out.

OBJ and STL export

Both export the same set: every shape that is closed and has a height above zero. An open reference line, or a footprint with no height yet, is excluded from either. Neither format ever touches an imported reference model — see below. STL is written binary, with every vertex and normal stored as a 32-bit float; OBJ is written as plain text, full double precision, no rounding.

OBJ import

An imported .obj becomes a static reference, kept apart from the drawn shapes in its own group from the moment it loads. It is never written into the project's shape list, so it can be moved, scaled and deleted, but never edited as geometry — and it never exports again. Draw over it, extrude your own footprint from it, but the file you imported does not travel back out.

Image import

You are asked for one number: the image's real-world width, in metres. Height is never asked for — it is always the width you gave, multiplied by the image's own pixel aspect ratio, so the underlay can be resized without ever distorting.

PNG export

Captures the 3D view only, at whatever it currently shows — the 2D plan is a separate canvas and is never captured. If a shape is selected, its outline is genuine 3D scene geometry, so it appears in the image; if a reference model is selected, its handle does too. A push/pull cursor is styling on the pointer, not scene content, so it never shows.

Save and open

A saved project is the entire state as JSON, with every imported image and model's raw data folded in alongside it. Opening it reverses that exactly. This is the one format that is fully round-trip safe, imported assets included.

The round trip, plainly

Draw, export DXF, re-import the DXF: you get the same editable shapes back, by design. Draw, export OBJ or STL: nothing re-imports either back into editable geometry — an imported .obj only ever becomes a static reference, never a drawn shape. Save, then open: everything comes back, including imported images and models. Those are the only three round trips this tool has, and only one of them is lossless in both directions.

05

How exact the numbers are

The arithmetic itself is exact — there is no approximation, no solver converging on an answer, nothing to be near. The honest question is one of resolution and representation instead: what the grid costs you, what an export keeps, and what the tool actually guarantees.

What the grid costs

With Snap on, the smallest difference a newly drawn point can express is one grid unit — one metre, by default. That guarantee holds only at the instant a shape is created; trap 1 covers why it does not survive a move or a scale. The grid size itself has no fixed range in the source — any positive number can be typed into the toolbar's grid field.

Precision in the exports

DXF and OBJ both write coordinates at full double-precision JavaScript numbers, with no rounding applied anywhere in either exporter. STL is the one exception, and for a physical reason rather than a design choice: the binary STL format itself stores every vertex and normal as a 32-bit float, so re-importing an STL loses precision the DXF or OBJ export of the same model would not.

A non-snapped point is easy to produce

Turn Snap off and draw normally, or leave Snap on and simply move or scale a shape afterwards — trap 1 again. Either way, nothing marks the resulting coordinates as off-grid; they look the same as a snapped point everywhere they are displayed.

Where a wall push/pull can go wrong

The side-wall and radius drags carry three safety limits, and none of them is a correctness guarantee. The wall drag is rejected if it would shrink the shape's area below five per cent of what it started at — this catches an obvious collapse, but area alone cannot catch every way a polygon can fold in on itself; a drag that leaves the area roughly unchanged while crossing one of the shape's own non-adjacent edges is not guarded against. When the two edges neighbouring the one being dragged are near-parallel to it, the two corners the drag should reconstruct by intersecting lines cannot be found that way, and the code falls back to moving both corners in a straight line instead — a reasonable approximation, not the same geometric operation as the general case. The drag distance itself is separately clamped to five hundred units in either direction, a safety limit against a rare instability in the ground-plane arithmetic at a grazing camera angle, not a meaningful design constraint; a circle's radius is clamped between 0.05 and 1000 units by the same drag.

What is actually asserted

The solid you see is the footprint you drew, extruded by the layer's height or by however far you dragged it, and nothing more. There is no automated test suite anywhere in this application's source — no test files, no test script, nothing. What the tool computes has been read from the code for this page; it has not been checked against itself by any suite of its own.

07

Compared with SketchUp, BIM and a CAD package

Where it agrees

  • Push/pull. Dragging a shape's top face to change its height, or a side wall to move just that wall, is the same operation SketchUp's push/pull tool performs on a pushed face. The mechanics match; nothing here checks the result against anything.
  • Plan-to-solid workflow. Draw a footprint, give it a height, and you have a massing volume — the same first move a SketchUp or Rhino study starts with.
  • DXF as a real interchange format. The DXF this tool writes and reads uses standard entity types a CAD package expects, closed as connected polylines rather than loose lines.

Where it diverges

  • No object model beyond a footprint and a height. A Revit wall carries a type, a thickness, layers, and relationships to the walls, floors and rooms around it. A Massing Studio "wall" is one side of an extruded rectangle — geometry, a colour, and nothing else. There is no wall object here to compare.
  • No BIM metadata of any kind. No IFC classes, no element properties, no schedules, no quantities beyond what you would measure off the model yourself.
  • No analysis. Nothing here computes a structural, thermal, daylight or cost quantity — trap 3 again. A BIM tool with an analysis link, or a dedicated analysis package, is what that question needs.
  • No parametric relationships. Move one shape and nothing else in the model reacts to it, because nothing here knows the shapes are related at all.

The honest place for this tool: a fast way to test a footprint and a few storeys against each other before opening something heavier. Move to SketchUp, Rhino or a BIM package the moment you need materials, assemblies, or an answer that has to be checked rather than sketched.

08

Three exercises

Each isolates one variable and holds everything else fixed. Read the model, not the picture.

Exercise 01

Footprint depth governs how much of a room is daylit

  1. Draw a single rectangle 6 m wide. Set its height to one storey.
  2. Extend its depth from 6 m to 18 m in three steps, redrawing or dragging a side wall each time — the tool's own push/pull, applied to one wall only.
  3. At each depth, mark by eye how far daylight from the 6 m face is likely to reach into the plan — roughly twice the window head height is the usual rule of thumb, applied here entirely outside the tool.
  4. Note the depth beyond which the far end of the room falls outside that reach.

Principle. The tool has no daylight model of any kind — trap 3 and the "Not modelled" ledger both say so. What it gives you is an exact footprint to measure a rule of thumb against by hand, which is a different and more honest use of the tool than expecting it to answer the question itself.

Exercise 02

The same floor area takes very different forms once storeys change

  1. Draw a footprint and extrude it to one storey. Read its plan dimensions and, using the shoelace formula this page names in section 01, compute its area by hand — the tool will not do this for you (trap 2).
  2. Redraw a second footprint at a quarter of the plan area, and extrude it to four storeys instead.
  3. Compare the two massing volumes in the 3D view. Note that their total floor area is the same by construction, and their footprint and massing are not.
  4. Try a third: half the footprint area, two storeys, and see where it sits between the other two.

Principle. Because the tool never computes or displays an area, comparing options by floor area is entirely the student's own arithmetic — exactly the point of trap 2. The tool's job is to make the volumes visible once you have decided what to compare.

Exercise 03

A massing exported as .obj becomes another tool's input

  1. Build a simple massing study — a footprint or two, extruded to a few storeys.
  2. Export it as .obj (section 03 above covers exactly what does and does not travel with it — no colour, no layer, geometry only).
  3. Import that .obj into Solar Analysis Lab or 3D Wind Rose, both of which read the same format.
  4. Note what each tool then does with the geometry that Massing Studio itself has no way to compute.

Principle. This is the strongest argument for where Massing Studio sits in the set: it is not the tool that answers a solar or wind question, it is the tool that produces the geometry those questions are asked of. The .obj export exists for exactly this handoff.

A caution for all three: read the model, not a number the tool never gives you. Where a figure matters, compute it yourself and say how.

Everything on this page was read from the tool's source code. Where a claim could be checked against the code directly, it was; where the code did not make something clear, this page says so rather than inferring.

For anything beyond an early massing study, use the appropriate analysis tool. This tool is built to teach the relationship between a plan and a volume, and it contains no analysis of any kind — deliberately, so that what it does do stays legible.
